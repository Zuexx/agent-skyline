# 效能

[English](performance.md)

2026-10-09 量測:Windows 11、RTX 4090、Chrome(無頭模式,GPU 經 ANGLE/D3D11)、畫面 1600×900、夜間主題。測試用的 repo 是合成的(`bench/make-repo.mjs`):檔案分散在最多四層資料夾,每個檔案 1 到 400 行。

## 伺服器

| 檔案數 | 資料夾(街區) | 掃描 | 版面 | `/api/city` JSON |
|---:|---:|---:|---:|---:|
| 518(forgekit) | 234 | 1.8 秒* | 2 ms | 80 KB |
| 5,000 | 1,841 | 258 ms | 10 ms | 545 KB |
| 20,000 | 1,841 | 963 ms | 19 ms | 1.85 MB |

\* forgekit 那次是開機後第一次掃描(磁碟快取是冷的),合成 repo 是熱的。掃描只在啟動和重新掃描時執行;版面計算很便宜,每次切換分組都可以在瀏覽器重算。

## 瀏覽器,20,000 個檔案

同一個 Chrome、同一個腳本(`bench/perf.mjs`),連線時重送 3,000 筆歷史事件,量測期間每秒 10 筆即時事件。

| | 優化前 | 優化後 |
|---|---:|---:|
| 主執行緒忙碌比例 | 44% | 9% |
| 首次載入 | 2,054 ms | 133 ms |
| JS 記憶體 | 79 MB | 36 MB |
| 每秒影格 | 56 | 61(螢幕上限) |
| 8 倍速重播 | — | 61 fps,忙碌 14% |

在 Orca 內建的瀏覽器(資源較少)裡,優化前的版本掉到每秒約 2 格,分頁直接卡死。

### 改了什麼

1. **動態列表每次更新都把整段歷史畫出來**(最多 1,000 列),每秒 10 次。現在只畫 120 列,捲動時再增加;每一列都做 memo,並使用穩定的 callback,沒變的列不重畫。
2. **每個資料夾都是獨立的 mesh 和 React 元素**:每次更新要比對 1,841 個元素、發出 1,841 次繪製呼叫。現在所有資料夾合成一個 `InstancedMesh`,點擊時用實例編號找出是哪個資料夾。
3. **大樓上色每秒 4 次檢查全部 20,000 棟**。現在只檢查候選:有活動的檔案、比較中 diff 裡的檔案,以及目前不是預設顏色的大樓。

## 真實專案:VS Code(20,323 個檔案)

2026-10-09 用 `microsoft/vscode` 的淺層 clone 量測(20,323 個檔案、14,848 個 JS/TS 原始檔、4,602 個資料夾)。檔案數和合成 repo 一樣,但真實專案路徑長、資料夾深、有真的 import,因此找到五個合成 repo 測不出的問題:

| 問題 | 影響 | 修正 |
|---|---|---|
| `git ls-files` 輸出超過 1 MB(路徑長) | 伺服器根本打不開這個 repo(`ENOBUFS`) | 調高 `maxBuffer`,和 `git.mjs` 一致 |
| 城市深 1,880、相機距離約 2,300 | 城市大半被相機預設的遠裁切面(2,000)切掉 | 依城市大小設定遠裁切面 |
| 4,602 個街區,名稱用 drei `<Html>` | 縮放時一次建立、移除幾百個 React root,React 報錯(`removeChild`) | 名稱改成一層 DOM,由場景每格更新位置 |
| 依賴解析上限 8,000 個檔案 | 依字母順序截到一半:`src/vs` 大部分沒有道路 | 上限調到 40,000(每個檔案約 0.12 ms) |
| 139,456 條依賴以完整路徑成對傳送 | `/api/deps` 有 17 MB 的 JSON | 路徑只傳一次,依賴用編號:2.4 MB |

修正後的伺服器(第二次執行;第一次見下方):

| 步驟 | 時間 |
|---|---:|
| 掃描(檔案清單 + 行數) | 1.7–1.9 秒 |
| 版面配置 | 47 ms |
| 依賴解析(14,848 個原始檔、139,456 條) | 1.9 秒 |
| 近 90 天變動(churn) | 0.3 秒 |
| 未 commit 的改動 | 0.7 秒 |
| `/api/city` / `/api/deps` | 3.2 MB / 2.4 MB |

瀏覽器(方法同上:3,000 筆歷史事件、每秒 10 筆即時事件):首次載入 162–171 ms,主執行緒約 85% 閒置,8 倍速重播一樣順,JS 記憶體 37–42 MB。點選大樓並畫出依賴道路約 50 ms。

**第一次執行**:clone 後第一次掃描花了 146 秒,第二次 1.9 秒。掃描要開啟每個檔案算行數,而 Windows Defender 的即時保護(開著)會在第一次開啟時逐一掃描,這很可能是原因,但沒有證實。第一次 churn 花 44 秒,是因為 clone 只下載了部分內容(`--filter=blob:none`),偵測重新命名時要從網路抓檔案內容;churn 現在加了 `--no-renames`,完全不需要檔案內容。

**尚未解決**:資料夾層次很深時,版面配置會在街區之間留下大片空白,全景下 VS Code 的大樓顯得又小又稀疏。拉近看還可以,之後值得改善排列方式。

## 重現

```bash
cd codecity/bench && npm install
node make-repo.mjs /tmp/repo20000 20000
CODECITY_EVENTS=/tmp/perf/events.jsonl node ../server/server.mjs --repo /tmp/repo20000 --port 4479 --no-watch
node ../cli/simulate.mjs --repo /tmp/repo20000 --file /tmp/perf/events.jsonl --agents 4 --interval 100 --count 3000
node perf.mjs http://127.0.0.1:4479/ 8            # 或:... 8 replay
```

`perf.mjs` 驅動系統已安裝的 Chrome(`channel: "chrome"`),不會另外下載瀏覽器。
